Floppy Disk Shooting Game
Siv3D風エンジンAPIへの全面改訂指示書

作成日: 2026-08-22

======================================================================
0. この指示書の目的
======================================================================

現在、Unity風のGameObject／Component基盤が作業ツリーへ実装され始めている。
この実装を単純に削除するのではなく、利用価値のある内部機構を残しながら、
ゲーム開発者が触る公開APIをSiv3D風の軽量な設計へ全面改訂する。

最終目標:

- ゲームコードはScene、Entity、図形、描画、入力、音声を直接的に記述できる
- GameObjectへ多数のComponentを追加しないと何もできない構造にしない
- 描画はRendererへ図形や描画データを渡すだけで行える
- 当たり判定は図形同士のIntersectsで簡単に記述できる
- DirectX 12の詳細はゲームコードへ露出させない
- 既存のSceneManager、Time、Input、Audio、数学型を活かす
- 最終ビルド1.44MBという制約に合う小さなランタイムを維持する

この作業では、UnityやSiv3Dとの完全互換を目指さない。
Siv3Dの「C++で簡潔にゲームを書く」操作感を参考に、本ゲームに必要なAPIだけを作る。


======================================================================
1. 最重要ルール
======================================================================

1. ユーザーの既存変更をgit reset、checkout、restoreで破棄しないこと
2. 現在の差分を読み、必要な部分を移植してから不要部分を除去すること
3. 一度にゲーム本体まで全面移行せず、エンジンAPIを小さな単位で完成させること
4. 各段階でFloppyEngineとTestsをビルド・実行すること
5. Doxygenコメントを使用し、処理のまとまりには簡潔なコメントを書くこと
6. コメント末尾に句点を付けないこと
7. 公開APIへDirectX::XMFLOAT系を新規露出させず、Engine/Mathの型を使用すること
8. 新しい共有所有権が必要でない限りshared_ptrを増やさないこと
9. 実行時リフレクション、文字列メッセージ、汎用エディタ機構を作らないこと
10. まず2D APIを完成させ、3D APIは同じ設計思想で後から追加すること

- OnDisable

3. 採用する設計思想
======================================================================

ゲーム側はSceneがEntityの集合を所有し、各EntityがInitialize、Tick、Renderを持つ。
単純な弾やアイテムは継承を使わない構造体でもよい。

例:

class Player {
public:
    void Initialize();
    void Tick();
    void Render(Renderer& renderer) const;

    Circle Bounds() const;
    const Vector3& Position() const;

private:
    Vector3 m_position {};
    Vector3 m_velocity {};
};

class StageScene final : public IScene<SceneType, SceneSharedData> {
public:
    void Initialize() override;
    void ProcessInput() override;
    void Tick() override;
    void Render(Renderer& renderer) override;
    void Shutdown() override;

private:
    Player m_player;
    std::vector<Enemy> m_enemies;
    ObjectPool<Bullet> m_bullets;
};

描画例:

renderer.Draw(Circle { position, 12.0f }, ColorF { 0.2f, 0.8f, 1.0f });
renderer.Draw(Rect { position, size }, ColorF::White());
renderer.Draw(mesh, transform, material);
renderer.DrawText(font, "SCORE", position, ColorF::White());

当たり判定例:

if (player.Bounds().Intersects(enemy.Bounds())) {
    player.Damage(1);
}

図形自身のDraw()は第一版では採用しない。
Circle::Draw()がグローバルRendererへ依存するより、Renderer::Draw(Circle)の方が
依存関係とテスト容易性に優れるためである。


======================================================================
4. 公開APIの命名規則
======================================================================

本プロジェクトでは以下を標準とする。

- 初期化: Initialize
- 状態更新: Tick
- 固定時間更新が明確に必要な内部処理: FixedTick
- 描画: Render
- 終了処理: Shutdown
- 有効状態: SetEnabled／IsEnabled
- 座標取得: Position
- サイズ取得: Size
- 図形描画: Renderer::Draw
- 文字描画: Renderer::DrawText
- 衝突判定: Intersects
- 点包含判定: Contains

禁止する公開名:

- Awake
- Start
- Update
- FixedUpdate
- LateUpdate
- MonoBehaviour
- OnEnable
- OnDisable
- OnDestroy

内部のフレーム処理関数についても、可能な限りTick系へ統一する。

8. Phase 2: Transformの救済と整理
======================================================================

Luna実装のTransformは再利用する。

作業内容:

1. TransformをDomain/EntitiesからEngine/SceneまたはEngine/Mathへ移す
2. DirectX::XMFLOAT3をVector3へ置き換える
3. オイラー角の内部保存を再検討し、可能ならQuaternionを使用する
4. 次の重複APIを統一する
   - position()とPosition()
   - localPosition()とLocalPosition()
   - worldMatrix()とWorldMatrix()
5. 公開APIをPascalCaseへ統一する
6. 親子階層、Dirty伝播、循環防止は維持する
7. GameObjectとの互換アクセサーは移行期間だけ残す
8. TransformテストをTimeTests.cppから専用TransformTests.cppへ移す

第一版API:

class Transform {
public:
    const Vector3& LocalPosition() const;
    void SetLocalPosition(const Vector3& position);

    Vector3 Position() const;
    void SetPosition(const Vector3& position);

    const Quaternion& LocalRotation() const;
    void SetLocalRotation(const Quaternion& rotation);

    const Vector3& LocalScale() const;
    void SetLocalScale(const Vector3& scale);

    void Translate(const Vector3& distance);
    bool SetParent(Transform* parent, bool keepWorldTransform = true);
    Transform* Parent() const;
    std::size_t ChildCount() const;
    Transform* Child(std::size_t index) const;
    const Matrix4x4& WorldMatrix() const;
};

SetParentは失敗理由を呼び出し側が判定できるようboolを返す。

完了条件:

- DirectX型を使わずTransformを操作できる
- 親の移動・回転・拡縮が子へ正しく反映される
- keepWorldTransformが正しく機能する
- 親子循環を拒否する
- 専用テストが通る

9. Phase 3: 基本図形と色
======================================================================

最初に実装する新しいSiv3D風APIは基本図形である。

追加ファイル:

- Engine/Graphics/Color.h
- Engine/Geometry/Circle.h/.cpp
- Engine/Geometry/Rect.h/.cpp
- Engine/Geometry/Line.h/.cpp（必要最小限）
- Tests/GeometryTests.cpp

ColorF:

struct ColorF {
    float r = 1.0f;
    float g = 1.0f;
    float b = 1.0f;
    float a = 1.0f;

    static constexpr ColorF White();
    static constexpr ColorF Black();
    static constexpr ColorF Red();
    static constexpr ColorF Transparent();
};

Circle:

struct Circle {
    Vector2 center {};
    float radius = 0.0f;

    bool Contains(const Vector2& point) const;
    bool Intersects(const Circle& other) const;
    bool Intersects(const Rect& other) const;
};

Rect:

struct Rect {
    Vector2 position {};
    Vector2 size {};

    Vector2 Center() const;
    bool Contains(const Vector2& point) const;
    bool Intersects(const Rect& other) const;
    bool Intersects(const Circle& other) const;
};

規則:

- 負の半径やサイズの扱いを明文化する
- 判定は描画APIやDirectXへ依存させない
- CircleとRect間の結果は呼び出し方向によらず一致させる
- 境界上を衝突とみなす

完了条件:

- 図形だけで当たり判定を記述できる
- GeometryTestsがウィンドウなしで実行できる

10. Phase 4: Rendererファサードと描画コマンド
======================================================================

目的:

Temp/ShootingGame.hが定数バッファ、パイプライン番号、DrawInstancedを直接扱っている
状態を解消する。

追加する概念:

- Renderer
- RenderCommand
- PipelineId
- Camera2D
- Camera3D

第一版Renderer API:

class Renderer {
public:
    void BeginFrame();
    void Draw(const Circle& circle, const ColorF& color);
    void Draw(const Rect& rect, const ColorF& color);
    void Draw(const MeshHandle& mesh,
              const Transform& transform,
              const MaterialHandle& material);
    void DrawText(std::string_view text,
                  const Vector2& position,
                  float size,
                  const ColorF& color);
    void EndFrame();
};

RenderCommandは固定容量またはフレームアロケータで保持し、ゲーム側のDraw呼び出し順を
基本順序として記録する。必要な不透明物だけ後からMaterial単位でソートする。

禁止事項:

- Renderer公開APIからID3D12GraphicsCommandListを返さない
- ゲーム側へ定数バッファのindexを渡さない
- SetPipelineState(int)を新規コードで使用しない
- アスペクト比を800/600などで固定しない

移行期間はD3D12RenderingServiceをRenderer内部のBackendとして包む。

完了条件:

- CircleとRectをRenderer::Drawで描画できる
- ゲームコードが定数バッファへ直接書き込まない
- パイプライン指定が型付きである
- ウィンドウサイズからアスペクト比を計算する

11. Phase 5: EntityとObjectPool
======================================================================

Player、Enemy、BulletをGameObject／Componentの組み合わせではなく、ゲーム固有の型へ
移行する。

例:

struct Bullet {
    Vector3 position {};
    Vector3 velocity {};
    float radius = 0.5f;
    bool active = false;
    bool enemy = false;

    void Initialize(const BulletSpawnData& data);
    void Tick();
    void Render(Renderer& renderer) const;
    Sphere Bounds() const;
};

ObjectPool<T>:

- コンテナはstd::vector<T>または固定長配列
- Spawn時に未使用要素を返す
- 上限到達時の挙動を明確にする
- Despawnはactive=falseを基本とする
- 破棄ごとの動的メモリ確保を避ける

PrefabRegistryは当面実装しない。必要な生成処理はFactory関数またはSpawnDataで表現する。

完了条件:

- BulletがGameObjectなしでTick／Render／Boundsを提供する
- 弾の生成と消滅でヒープ確保が発生しない
- 既存の最大500弾を管理できる


======================================================================
12. Phase 6: CollisionServiceの再編
======================================================================

二つの用途を分ける。

A. 単純なゲーム判定

- Circle::Intersects
- Rect::Intersects
- Sphere::Intersects
- Box::Intersects

B. 登録型の衝突システムが必要な場合

- CollisionServiceを残す
- previousPairsとcurrentPairsを保持する
- Enter／Stay／Exitを正しく分類する
- Collider登録解除を安全にする
- LayerとMaskを使用する

シューティングの弾対敵など、処理対象が明確な判定はAを優先する。
物理世界へ全オブジェクトを登録する方式を必須にしない。

完了条件:

- Temp/ShootingGame.hの手書き距離判定を図形APIへ置き換えられる
- 登録型を使う場合、接触開始時にEnterが一度だけ発生する


======================================================================
13. Phase 7: Scene APIの整理
======================================================================

既存SceneManagerはSiv3D風設計と相性が良いため維持する。

ISceneの最終候補:

class IScene {
public:
    virtual ~IScene() = default;
    virtual void Initialize() = 0;
    virtual void ProcessInput() = 0;
    virtual void Tick() = 0;
    virtual void Render(Renderer& renderer) const = 0;
    virtual void Shutdown() {}
};

固定時間更新はメインループがTickを固定間隔で呼ぶ現行方式を維持してよい。
可変Tickと固定Tickの両方が本当に必要になった場合だけFixedTickを追加する。

SceneManager:

- addSceneは既存互換のため残してよい
- 新規APIはAddSceneなどプロジェクト規約に合わせて統一する
- Scene遷移要求はフレーム境界で反映する
- Scene間共有データを維持する
- 将来的なフェード遷移はSceneTransitionとして分離する

======================================================================
19. 最終判断
======================================================================

Lunaが書いたコードを全面的に捨てる必要はない。

Transformは今後のCamera、複合機体、3D描画にも有用なので残す。
GameWorldの遅延破棄も、将来必要なら内部実装として活用できる。

一方、MonoBehaviourとUnity固有ライフサイクルは本ゲームの公開APIから撤去する。
ゲーム開発者が触る中心はScene、Entity、Geometry、Renderer、Input、Time、Audioとし、
Initialize／Tick／Render／Shutdownによる単純な流れへ統一する。

最初の実装はUnity風コードの撤去ではなく「Transformを救済しながら公開面を整理する」
作業として行う。その後、ColorF、Circle、Rect、Renderer::Drawの順でSiv3D風APIを
育てること。
